# 测试方案

本文件定义"怎么测"。任何框架的测试都必须严格照此执行，偏离要在 `PROGRESS.md`
里写明原因。

---

## 一、公平性约束（最重要的一节）

不同框架之间唯一允许的差别，是 `frameworks/<名字>/adapter.py` 里那点实现。
其余全部由 harness 固定：

| 项目 | 统一口径 |
|---|---|
| 输入数据 | 同一份 `data/`，同一时间顺序 |
| 单条记忆的文本表示 | `[ISO时间戳] 说话人：正文`，由 `Utterance.as_text()` 生成 |
| 问题文本 | `question_set.json` 原文，一字不改 |
| 提问顺序 | 按 qid 升序 |
| top-k | 统一 8（`adapters/base.py:DEFAULT_TOP_K`）；框架不支持则在 `describe()` 注明 |
| 系统提示词 | `adapters/base.py:SYSTEM_PROMPT`，带 LLM 生成的框架必须原样使用 |
| LLM | 全部框架用同一个模型、同一组采样参数 |
| Embedding | 全部框架用同一个模型 |
| 判分 | 同一套 `harness/scorer.py` 规则 + 同一份人工复核表 |

**禁止事项**：适配器里不得出现针对本问题集的特殊提示词、关键词硬编码、答案后处理。
那样测出来的是 prompt 工程水平，不是框架能力。

一个框架若因为架构原因做不到上面某一条（例如无法指定 top-k、无法换 embedding），
这本身就是一项要写进报告的能力差异，不是可以私下绕过的细节。

## 二、数据

- 生成器：`scripts/gen_data.py`，固定随机种子 `20260310`，任意机器重跑产出一致。
- 时间窗：2026-03-02（周一）~ 2026-03-31，共 30 天。起始日选周一，是为了让
  "上周三"这类相对时间表达能无歧义地对齐。
- 规模：3 场景共 430 条对话、39 条事实，其中 9 条状态型事实在中途被新版本取代。

| 场景 | 对话 | 事实（状态/事件） | 中途变更的事实 |
|---|---|---|---|
| eldercare 养老院长者 | 154 | 6 / 8 | 降压药、书法班时间 |
| pet 宠物主人 | 132 | 8 / 6 | 主粮、喂食量、体重×2 |
| robot 机器人任务日志 | 144 | 6 / 5 | 充电桩位置、耗材库房、工位 |

- **`facts_timeline.json` 是答案的唯一来源**。每条事实带 `valid_from` /
  `valid_to` / `supersedes` / `superseded_by` / `evidence`，对话文本由它渲染而来。
  这保证标准答案永远不会和数据脱节。
- 生成器自带一致性自检：状态事实的版本链必须首尾相接、无空洞无重叠，
  `supersedes` 指针必须对称，每条事实必须有对话证据支撑。

> **本批数据为模拟数据**。报告中所有结论必须标注这一点；真实转写数据到位后，
> 至少要重测事实变更、跨会话综合、拒答三类关键项。

## 三、问题集

`question_set.json`，共 60 题，5 类 × 各 12 题，3 个场景各 20 题。

| 类型 | 题数 | 考察点 |
|---|---|---|
| `fact_recall` | 12 | 某人某天说过/发生过什么 |
| `temporal_locate` | 12 | 按时间锚点检索，含"上周三下午"这类相对表达 |
| `fact_change` | 12 | 新旧事实覆盖；其中 3 题按历史时点回溯提问 |
| `cross_session` | 12 | 需要拼接多天信息（计数、比较、因果） |
| `refusal` | 12 | 数据中不存在的事，看框架会不会瞎编 |

**相对时间约定**（写在 `question_set.json` 的 `relative_time_convention` 字段里）：

- "上周三" = 提问日所在自然周（周一为一周之始）的前一周的周三
- "上午" = 06:00–12:00，"下午" = 12:00–18:00，"晚上/夜里" = 18:00–次日 06:00

**每题字段**：`as_of`（提问时点）、`gold_answer`、`gold_evidence`（指向具体
utt_id）、`scoring`（机器判分规则）、`llm_judge_rubric`（人工/LLM 判分口径）。

**3 道回溯题**（`requires_as_of: true`）值得单独关注：它们问的是"截至某个历史
日期，当时的事实是什么"。只保留最新事实的框架会答成新值，这是区分
"有时间维度的记忆"和"只是个向量库"的关键分水岭。

### 问题集的自动校验

`scripts/gen_question_set.py` 在产出前会逐题校验，任何一条不过就拒绝写文件：

- 证据用「第几天 + 原文片段」定位，必须在那一天里唯一命中一条对话
  （避免人工誊抄 utt_id 出错——第一版就是这么被抓出 10 处错的）
- 判分关键词必须真的能在证据原文里找到；计数、差值这类推导型答案需显式声明
  `derived` 才能豁免
- 拒答题声明的探针词必须在整个场景语料中**一次都不出现**，词组不得在同一条
  对话中共现——这才能保证"数据里确实没有这件事"
- 变更题声明的旧值必须真的在语料里存在，否则这道题立不住
- 每类题数不少于 10

## 四、指标定义

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 准确率 | 逐题对/错，分总体、分题型、分场景 | 自动初筛 + 人工复核，**报告以人工列为准** |
| 检索延迟 P50/P95 | 单次 `query()` 的墙钟毫秒数，线性插值分位 | `harness/metrics.py` |
| 灌入 token | ingest 阶段总消耗 | 适配器自报 |
| 查询 token | 单次查询平均 in/out | 适配器自报 |
| 内存峰值 | 进程 RSS 峰值（MB） | `ru_maxrss` + 200ms 采样 |
| 显存峰值 | 全部 GPU 已用显存峰值（MB） | pynvml，无 GPU 记 `null` |
| 证据召回率 | 检索命中的 `gold_evidence` 占比 | harness 自动计算 |

**内存指标的重要注意事项**：`ResourceMonitor` 只能看到 runner 自己这个进程。
Letta、Graphiti 这类把重活放在独立服务或 Docker 容器里的框架，进程内数字会严重
偏低。这种情况必须另行用 `docker stats` 等手段补齐，并在报告里注明口径，
**不许拿进程内数字冒充框架总占用**。

**token 计数口径**：装了 tiktoken 就用 `cl100k_base`；没装则退化为启发式
（一个中日韩字符约 1 token，拉丁词约 0.75）。用的是哪一种会写进
`summary.json` 的 `environment.tokenizer`。同一轮对比必须用同一种口径。

## 五、判分规则

自动判分只做可机械核对的部分，判完一律导出 `review.csv` 供人工复核。
三条规则（实现见 `harness/scorer.py`）：

- **`keywords`**：`must_include` 全中，且每个 `any_of` 组至少中一个。
- **`supersede`**（变更题）：在 keywords 基础上额外查旧值。旧值出现在回答里**本身
  不算错**——"之前是 A，现在是 B" 是完全正确的回答——但旧值前后 25 字窗口内必须有
  转折标记（之前/原来/已停/改为/换成…），否则视为把旧事实当成现行事实，判错。
- **`refusal`**：必须出现拒答表述，且不得出现任何被禁词。给出了具体的、数据中
  不存在的细节，即使加了"可能""大概"，一律判错。

比对时先做归一化：全角转半角、去空白、转小写。

自动判分会有误差（尤其是措辞灵活的跨会话题），所以 `review.csv` 里
`human_verdict` 和 `human_note` 两列留空，人工逐题过一遍，**报告中的准确率数字
取人工列**。自动列保留，用于说明两者差异有多大。

## 六、执行流程

每个框架走完全相同的六步：

1. **建环境**：`frameworks/<名字>/setup.sh`，独立 venv，记录安装耗时、依赖体积、踩坑。
2. **跑官方最小示例**：确认框架本身可用，再开始测。跑不通就记录原因并停在这一步。
3. **写适配器**：`frameworks/<名字>/adapter.py`，实现 `MemoryAdapter` 接口。
4. **跑测试**：激活该框架的 venv，`python3 -m harness.runner --framework <名字>`。
5. **人工复核** `review.csv`，填 `human_verdict`。
6. **更新 `PROGRESS.md`**，记录踩坑与结论。

跨 venv 的处理：harness **只依赖标准库**，所以可以在任意一个框架的 venv 解释器
下直接运行，不需要各 venv 反过来安装 harness 的依赖。

## 七、基线

`harness/adapters/baseline_bm25.py` 是一个零依赖的 BM25 检索基线，作用有三：

1. 在没有网络、没有 GPU、没有任何模型权重的机器上验证整条流水线；
2. 给出对比下限——记忆框架若打不过几十行的 BM25，那层"记忆"就没创造价值；
3. 隔离变量——它不调用 LLM，得分完全来自检索质量。

它的两个先天特点必须在报告里注明，**不可与带生成能力的框架直接比总分**：

- 没有生成环节，"回答"就是拼接检索到的原文。措辞类判分对它有利，需要归纳、
  计数、比较的题基本答不对。
- 它天然支持 `as_of` 过滤（直接按时间戳裁剪候选），而这是不少框架没有的能力。

另外，它的弃权阈值 `SCORE_FLOOR = 1.0` 是先验设定的，**没有针对本问题集调过**。
调高它能提升拒答类得分、但会牺牲召回；刻意去调这个数以美化基线分数，属于宪法
第 5 条禁止的"凑数据"。

## 八、附加评估（不需要跑测试，查资料 + 读源码）

每个框架都要回答这几个问题，写进报告：

- **记忆表示方式**（向量 / 图 / 文件）及**可解释性**：出了错能不能定位到是哪条
  记忆的问题？能不能把一条错误记忆单独删掉或改掉？
- **多模态扩展性**：图像、位置、传感器数据能否纳入记忆？是原生支持还是要自己塞
  进 metadata？
- **License、自托管成熟度、社区活跃度**：近 90 天 commit 数、issue 平均响应时间、
  是否有商业公司在维护、自托管路径是否是一等公民。
- **与"通用核心 + 专用 schema"架构的适配度**：加自定义字段（用药记录、宠物行为
  标签）有多难？是改配置、写插件，还是得改源码？
- **端侧可行性**：从依赖清单倒推能否在 Jetson（ARM64、8–16GB 内存）上跑。
  重点看有没有 ARM64 无预编译轮子的依赖、有没有强制的数据库/容器依赖、
  最小内存占用估计。**不实机测**，给出依赖层面的结论和最低配置估计。
